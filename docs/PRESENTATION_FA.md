# پیش‌نویس ارائهٔ فارسی OpsCustodian

این پیش‌نویس برای یک ارائهٔ ۱۰ تا ۱۲ دقیقه‌ای نوشته شده است. روایت از یک مسئلهٔ واقعی در کار روزانهٔ DevOps شروع می‌شود، بعد فایده و ریسک Agentها را نشان می‌دهد و در پایان به جایگاه واقعی OpsCustodian در آلفای عمومی می‌رسد.

## اسلاید ۱ — ساعت سهٔ بامداد؛ یک همکار نرم‌افزاری در حال بررسی رخداد

**متن کوتاه روی اسلاید**

یک هشدار جدی آمده است: زمان پاسخ API بالا رفته و انتشار آخرین نسخه مشکوک است. یک Agent لاگ‌ها و متریک‌ها را می‌خواند، تغییرات اخیر را پیدا می‌کند و پیشنهاد rollback می‌دهد.

**یادداشت اجرا**

Agent را مثل یک همکار نرم‌افزاری معرفی کنید: سریع است، خسته نمی‌شود و می‌تواند چند منبع را کنار هم بگذارد؛ اما برای بررسی یا اصلاح، به هویت و دسترسی نیاز دارد.

**پیشنهاد تصویر یا دمو**

تصویر سادهٔ یک خط زمانی از هشدار، بررسی لاگ، بررسی deployment و پیشنهاد rollback؛ بدون نمایش دادهٔ واقعی یا محرمانه.

## اسلاید ۲ — چرا Agent برای زیرساخت جذاب است؟

**متن کوتاه روی اسلاید**

Agent می‌تواند در چند ثانیه بین لاگ، متریک، repository، ticket و کلاستر ارتباط پیدا کند. کارهای تکراری را کم می‌کند و پاسخ اولیه را سریع‌تر به تیم می‌رساند.

**یادداشت اجرا**

روی «کمک به تصمیم‌گیری» تأکید کنید، نه جایگزینی مسئولیت انسانی. سرعت و پوشش بیشتر زمانی ارزشمند است که مسیر دسترسی و نتیجه قابل بررسی بماند.

**پیشنهاد تصویر یا دمو**

یک دیاگرام که Agent را به لاگ، متریک، Git و Kubernetes وصل می‌کند؛ در هر اتصال فقط نام منبع دیده شود.

## اسلاید ۳ — دسترسی Agent کجا پنهان می‌شود؟

**متن کوتاه روی اسلاید**

قدرت Agent فقط در prompt نیست. workflow، تنظیمات MCP، secret reference، هویت Kubernetes، نقش RBAC و دستورهای واردشده از repository هم در دامنهٔ اثر آن نقش دارند.

**یادداشت اجرا**

توضیح دهید که هر قطعه جداگانه ممکن است بی‌خطر به نظر برسد، اما زنجیرهٔ هویت تا ابزار و منبع، «دسترسی مؤثر» را می‌سازد.

**پیشنهاد تصویر یا دمو**

نمودار مسیر: Agent ← هویت ← secret reference ← ابزار ← repository یا workload. مقدار secret نشان داده نشود.

## اسلاید ۴ — ریسک واگذاری دسترسی

**متن کوتاه روی اسلاید**

وقتی یک ابزار قدرت اقدام دارد، باید بدانیم یک تصمیم اشتباه تا کجا می‌تواند اثر بگذارد. تفاوت «یک workload با write» و «همهٔ workloadهای production با admin» یک تفاوت متنی کوچک نیست؛ تغییر دامنهٔ خطر است.

**یادداشت اجرا**

این اسلاید را با مثال موجود در دموی پروژه پیش ببرید: دسترسی از `kubernetes:production/apps/payments (write)` به `kubernetes:production/* (admin)` گسترش پیدا می‌کند.

**پیشنهاد تصویر یا دمو**

دو قاب قبل و بعد با یک workload در برابر wildcard روی production؛ کنار آن برچسب «critical» و توضیح کوتاه علت.

## اسلاید ۵ — فرق تغییر متن با تغییر معنایی

**متن کوتاه روی اسلاید**

یک diff معمولی فقط خط‌های تغییرکرده را نشان می‌دهد. بررسی معنایی می‌پرسد: چه قابلیتی بیشتر شد؟ دامنه wildcard شد؟ اثر از write به admin رسید؟

**یادداشت اجرا**

بگویید که این نگاه، نویز قالب‌بندی را از تغییر واقعی دسترسی جدا می‌کند و برای بررسی CI قابل فهم‌تر است.

**پیشنهاد تصویر یا دمو**

اجرای دستور زیر در ترمینال محلی:

```text
opscustodian diff examples/scope-expansion/agentbom.before.json examples/scope-expansion/agentbom.after.json
```

خروجی مورد انتظار: finding با شدت `critical` و شناسهٔ پایدار.

## اسلاید ۶ — OpsCustodian چه پرسشی را پاسخ می‌دهد؟

**متن کوتاه روی اسلاید**

کدام Agent، با کدام هویت، به کدام ابزار، credential، repository و محیط دسترسی دارد؛ و آیا این دسترسی خطرناک‌تر شده است؟

**یادداشت اجرا**

توضیح دهید که پاسخ بر پایهٔ evidence و مسیرهای قابل توضیح ساخته می‌شود. ابزار reference دسترسی را ثبت می‌کند، نه مقدار secret را.

**پیشنهاد تصویر یا دمو**

نمایی از تصویر موجود `docs/images/opscustodian-inventory-overview.png` یا گزارش HTML تولیدشده در دمو.

## اسلاید ۷ — مسیر دمو: از فایل‌ها تا Agent BOM

**متن کوتاه روی اسلاید**

اسکن repository → نرمال‌سازی در Agent BOM → گزارش HTML خودبسنده → مشاهدهٔ assetها، قابلیت‌ها، credential referenceها، رابطه‌ها و diagnostics.

**یادداشت اجرا**

دمو را کاملاً آفلاین و روی fixtureهای عمداً ریسکی اجرا کنید. این مسیر به مدل AI، کلاستر Kubernetes، database یا cloud account نیاز ندارد.

**پیشنهاد تصویر یا دمو**

GIF موجود `docs/images/opscustodian-demo.gif`، سپس اجرای دستورهای اسکن و report از `docs/DEMO.md`.

## اسلاید ۸ — خروجی برای بررسی و CI

**متن کوتاه روی اسلاید**

خروجی JSON و HTML برای بررسی انسانی، SARIF برای ابزارهای سازگار، severity threshold برای CI و policy evaluation برای تصمیم قابل توضیح.

**یادداشت اجرا**

این قابلیت‌ها را به‌عنوان قراردادهای آلفا معرفی کنید. finding توضیح و evidence خود را نگه می‌دارد تا تیم بداند چرا نتیجه صادر شده است.

**پیشنهاد تصویر یا دمو**

یک نمونهٔ ساده از گزارش finding در terminal و همان finding در SARIF؛ متن را کوتاه نگه دارید.

## اسلاید ۹ — مرزهای آلفا

**متن کوتاه روی اسلاید**

OpsCustodian در آلفا، دسترسی مؤثر را از پیکربندی و evidence نگاشت می‌کند؛ در لحظه با providerها مجوزدهی نمی‌کند، automation را اجرا نمی‌کند و جای Kubernetes admission، cloud IAM یا human review را نمی‌گیرد.

**یادداشت اجرا**

شفاف بگویید که نبودن finding به‌تنهایی اثبات نبودن ریسک نیست؛ syntax پشتیبانی‌نشده، indirection یا قابلیت provider ممکن است diagnostics یا inventory ناقص ایجاد کند.

**پیشنهاد تصویر یا دمو**

دو ستون کوتاه: «آنچه امروز تحلیل می‌شود» در برابر «آنچه هنوز مسئولیت تیم است». از آیکون قفل یا سپر به‌عنوان ادعای enforcement زنده استفاده نکنید.

## اسلاید ۱۰ — جمع‌بندی: یک لایهٔ evidence و policy

**متن کوتاه روی اسلاید**

Agentها سرعت و پوشش می‌آورند؛ دسترسی پراکنده ریسک می‌سازد. OpsCustodian در آلفای عمومی یک مسیر آفلاین برای دیدن دسترسی مؤثر، توضیح مسیر آن و تشخیص drift معنایی فراهم می‌کند تا تیم قبل از تغییر پرخطر، evidence قابل بررسی داشته باشد.

**یادداشت اجرا**

با دعوت به اجرای دموی پنج‌دقیقه‌ای و خواندن `docs/LIMITATIONS.md` تمام کنید. از عبارت‌های «کنترل زنده»، «جلوگیری قطعی» و «production-ready» استفاده نکنید.

**پیشنهاد تصویر یا دمو**

تصویر نهایی از زنجیرهٔ «configuration → evidence → Agent BOM → semantic diff → policy review» با تأکید بر review انسانی در انتها.

## متن پیشنهادی برای آغاز شفاهی

«فرض کنید ساعت سهٔ بامداد است و یک Agent برای بررسی اختلال production به لاگ، متریک و deployment دسترسی دارد. سؤال فقط این نیست که Agent چه کاری انجام داد؛ باید بدانیم با کدام هویت می‌توانست به کجا دست بزند و آیا دامنهٔ این دسترسی تغییر کرده است.»

## متن پیشنهادی برای پایان شفاهی

«OpsCustodian در این مرحله یک ابزار evidence و policy برای تحلیل آفلاین است: دسترسی را از روی configuration قابل مشاهده می‌کند، مسیر آن را توضیح می‌دهد و تغییر معنایی را برای بررسی تیم علامت می‌زند. تصمیم مجوزدهی و تغییر production همچنان با کنترل‌های مستقل و انسان مسئول باقی می‌ماند.»
