# OpsCustodian v0.6.0-beta.1

This first beta moves OpsCustodian from an offline public-alpha inventory tool
to a deliberately narrow, evidence-backed Agentic DevOps control plane. The
offline CLI remains the simplest entry point, while the supported server
contract is limited to the tested single-replica reference described below.
This release does not claim production readiness or high availability.

## Supported beta contract

The authoritative platform and runtime boundary is the
[Beta support matrix](../BETA_SUPPORT_MATRIX.md), and the reviewed trust and
residual-risk boundary is the
[First-beta threat model](../THREAT_MODEL.md).

The offline CLI is supported through the published Linux amd64/arm64, macOS
amd64/arm64, and Windows amd64 archives. It provides repository discovery,
Agent BOM generation, evidence-backed findings, semantic drift, policy checks,
and local terminal, JSON, YAML, SARIF, and self-contained HTML reporting without
requiring a database, cluster, provider credential, or AI model.

The control-plane beta reference is Linux amd64, exactly one server replica,
PostgreSQL 17.4 over certificate- and hostname-verified TLS, and OPA 1.21.3
static. It supports static Bearer credentials or the versioned multi-credential
registry, explicit API scopes and repository grants, immutable snapshot
history, current and lifecycle findings, audit history and retention, local
repository ingestion, and GitHub App installation authentication with the
published limitations.

Multi-replica or production HA, Kubernetes as a supported distribution, OIDC,
GitHub PAT, non-GitHub hosted providers, direct non-loopback HTTP exposure,
PostgreSQL versions other than 17.4, and a general-purpose server container are
not supported by this beta.

## Upgrade and rollback

The only supported source upgrade for this release is the consecutive upgrade
from `v0.5.0-alpha`. Skip-version upgrades, mixed-version rolling upgrades,
in-place schema downgrade, physical backup, and point-in-time recovery are not
supported.

Before upgrading, follow [Upgrades](../UPGRADES.md) and create a complete
custom-format logical backup using the PostgreSQL 17 client procedure in
[Backup and restore](../BACKUP_RESTORE.md). Verify the backup by restoring it
into a new empty database before changing the running binary. Startup applies
forward migrations transactionally and rejects missing, modified, or unknown
migration ledger entries.

After upgrade, verify readiness, repository and snapshot counts, Finding and
audit history, policy evaluation, and a clean restart. Rollback after a schema
change means stopping the beta binary, restoring the verified pre-upgrade
backup into a new empty database, and starting `v0.5.0-alpha` against that
restored database. Do not run the older binary against the migrated database.

## Included changes

- A versioned control-plane API provides contract discovery, readiness,
  repository inventory, immutable snapshots, organization graph queries,
  semantic historical drift, current Findings, Finding lifecycle, audit
  history, policy evaluation, and bounded snapshot ingestion.
- PostgreSQL persistence provides tenant-scoped immutable snapshots, Findings,
  audit events, retention, transactional migrations, idempotency, and
  fail-closed fenced writes.
- Authentication supports bounded multi-credential rotation, activation and
  expiration windows, granular scopes, repository grants, constant-time token
  checks, and last-known-good credential-file reload.
- RepositorySet ingestion supports bounded local checkouts and hardened GitHub
  App acquisition with immutable revisions, isolated ZIP materialization,
  strict redirect handling, cache coalescing, and secret-reference-only
  configuration.
- Policy evaluation uses a timeout-bounded local OPA process and returns strict,
  versioned allow/deny decisions while excluding policy payloads and evaluator
  errors from audit summaries.
- Operational controls include secret-minimized JSONL/PostgreSQL audit fan-out,
  a private bounded outage spool, readiness components, backup/restore and
  consecutive-upgrade procedures, release preflight, artifact verification,
  and repository hygiene checks.
- Public Agent BOM, Finding, policy, audit, API, RepositorySet, preflight, SARIF,
  and migration contracts are inventoried in the
  [First-beta contract freeze](../BETA_CONTRACT_FREEZE.md).
- The representative GitHub Actions, MCP, and Kubernetes fixture has 11
  reviewed evidence-backed Findings with a regression-locked false-positive
  review in [First-beta representative Finding review](../BETA_FINDING_REVIEW.md).

Environment-backed validation includes disposable PostgreSQL bootstrap,
authenticated ingestion, OPA execution, OpenTelemetry export, logical
backup/restore, migration rollback and reapplication, upgrade from
`v0.5.0-alpha`, database outage and spool replay, controlled latency,
connection-pool exhaustion, read-only and connection-admission failures,
snapshot-write contention, a fixed 30-minute load profile, and a progressive
capacity ramp. These results describe the published reference environment and
are not a universal availability or performance guarantee.

## Known limitations

The control plane is single-replica and is not an HA service. Experimental
leader-election, multi-replica, and Kubernetes assets do not expand the beta
support promise. The server binds to a literal loopback address and requires an
operator-managed TLS boundary for access from another process or host.

Offline analysis explains authorization implied by repository configuration;
it is not a live authorization decision from GitHub, Kubernetes, an MCP runtime,
or another provider. Parser coverage is intentionally conservative, and an
absence of findings is not proof that an automation path is safe.

GitHub App expiry-driven provider refresh, redirect, cancellation, and rate
limit behavior require exact-candidate evidence. CodeQL publication also
depends on repository Code Scanning being enabled. The release is not ready to
tag until every required item in the
[Beta release checklist](../BETA_RELEASE_CHECKLIST.md) is closed with retained
evidence.

## Installation and verification

Download the archive for the supported operating system and architecture
together with `SHA256SUMS` and `opscustodian.cdx.json`. Verify the archive hash
against `SHA256SUMS`, inspect the populated CycloneDX SBOM, and verify the GitHub
build-provenance attestation before extraction.

After extraction, confirm the embedded version and public contract registry:

```bash
opscustodian version --format json
```

The output must report `v0.6.0-beta.1` and the documented contract versions.
Follow [Installation](../INSTALLATION.md) for offline CLI setup. Operators using
the single-replica server must also complete the beta preflight and the database,
policy, credential, backup, and recovery procedures before accepting traffic.

## Feedback wanted

Useful beta feedback includes a sanitized missed asset, an incorrect effective
access path, a false-positive Finding with its non-sensitive evidence shape, an
upgrade or recovery step that is unclear, or an explanation that a platform
team cannot act on.

Do not place credentials, private keys, tokens, signed URLs, private repository
contents, customer data, database dumps, or raw production logs in a public
issue. Reduce the report to the smallest synthetic fixture that reproduces the
behavior.
